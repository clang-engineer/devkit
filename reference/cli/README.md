# CLI reference

`catalog.json`은 명령어 정의·사용 예시·도구 사이의 관계를 관리하는 원본이다. [cmdtreemap](../../cmdtreemap/)의 터미널과 독립 웹 도구, 블로그 CLI 지도가 사용한다. 치트시트 카탈로그와는 독립적이다.

## 지도의 목적

CLI 지도는 새로운 도구를 모아 놓는 목록을 넘어, 같은 작업이 어떤 방식으로 개선되고 어떤 환경에서 다른 선택이 유용해지는지 설명한다. 치트시트가 “어떻게 쓰는가”를 빠르게 찾아보는 자료라면, 지도는 “왜 이 도구를 선택하고 기존 도구는 언제 유지하는가”를 살펴보는 자료다.

[GeekNews의 모던 리눅스 도구 모음](https://news.hada.io/topic?id=23659)과 [원문](https://ikrima.dev/dev-notes/linux/linux-modern-tools/)은 도구를 발견하는 출발점으로 참고한다. 댓글에서 제시한 설치 부담, 환경 차이, 호환성 문제는 선택을 검토하는 질문으로 활용한다. 댓글의 경험을 전체 사용자의 채택 현황으로 일반화하지 않는다.

## 관계와 변화는 다른 축이다

대안·대체·보완·래퍼·특화는 두 도구 사이의 관계다. 아래 항목은 무엇이 달라지는지, 실제 사용의 중심이 이동했는지를 살펴보는 별도의 관점이다. 네 단계의 발전 순서나 우열 등급이 아니다. 한 관계가 여러 변화에 해당할 수 있다.

| 관점 | 확인할 질문 |
|---|---|
| 출력·조작 개선 | 하던 작업을 유지하면서 표시·입력·기본값을 더 편하게 만드는가? |
| 특정 환경에서의 대체 | 어느 작업과 환경에서 기존 도구 대신 선택하는가? |
| 작업 방식 변화 | 검색·선택·조합하는 흐름 자체가 달라지는가? |
| 생태계 중심 이동 | 연동·문서·유지보수의 중심이 실제로 이동했는가? 근거와 시점은 무엇인가? |

기능상 대체할 수 있다는 것과 사용자들이 실제로 대체했다는 것은 별개의 주장이다. GitHub 별 수, 구현 언어, “modern”이라는 소개만으로 중심 이동을 판단하지 않는다. 유지보수 이력, 공식 마이그레이션 안내, 확인 가능한 연동 변화가 있으면 대상 범위와 확인 시점을 함께 기록한다. 근거가 없으면 채택 추세 대신 기능과 선택 조건까지만 설명한다.

## 같은 사용 흐름을 개선하는 경우

### cat과 bat: 파일 읽기의 표현 개선

파일을 지정하고 내용을 읽는 익숙한 흐름을 유지하면서, bat은 구문 강조·줄번호·Git 변경 표시와 자동 페이징을 제공한다. 파일을 더 잘 읽게 해주는 개선과 새 작업 방식의 도입을 구분한다.

“bat은 스크립트에서 cat을 대체할 수 없다”는 단정도 정확하지 않다. [공식 문서](https://github.com/sharkdp/bat#file-concatenation)에 따르면 비대화형 출력에서는 장식 없이 파일 내용을 출력한다. 다만 기본 설치 여부, 옵션과 설정의 차이까지 사라지는 것은 아니므로 기존 스크립트의 명령을 일괄 치환하지 않는다. 대화형 열람에서 얻는 이점과 자동화에서 요구하는 재현성을 따로 평가한다.

### grep과 ripgrep: 검색 범위의 기본값도 달라짐

[공식 문서](https://github.com/BurntSushi/ripgrep)에 따르면 ripgrep은 기본적으로 재귀 검색하며 ignore 규칙을 존중하고 숨김·바이너리 파일을 제외한다. 단순히 더 빠른 grep이라고만 설명하면 검색 결과가 달라지는 이유를 놓친다. 로컬 코드 검색에서는 편한 기본값일 수 있지만, 빠짐없이 검사해야 하는 작업에서는 검색 범위부터 확인해야 한다. 명령어 옵션 전체가 호환되는 drop-in replacement로 취급하지 않는다.

### ls와 eza: 표시 정보와 호환성의 분리

[eza](https://github.com/eza-community/eza)는 파일 유형·메타데이터·Git 정보 등 목록을 읽는 데 필요한 정보를 확장한다. 파일 목록을 보는 목적은 같지만 옵션이 ls와 완전히 같지는 않다. 개인 환경에서의 표시 개선과 공유 스크립트의 호환성을 같은 판단으로 묶지 않는다.

## 익숙한 입력을 유지하는 도입 방식

새 도구를 사용한다고 항상 명령 이름과 손에 익은 입력을 바꿔야 하는 것은 아니다. Alias는 익숙한 입력을 다른 실행 명령으로 확장해 머슬메모리를 유지하는 방법이다. 관계 유형과는 별도의 도입 방식이며, 이름이 같아져도 옵션·입력·출력의 호환성이 생기는 것은 아니다.

| 방식 | 입력 습관 | 확인할 점 |
|---|---|---|
| 기존 이름에 alias | cat처럼 손에 익은 이름 유지 | 전달되는 옵션과 기본 동작의 차이 |
| 익숙한 단축 이름 재사용 | ll 같은 개인 단축 이름 유지 | 기존 단축키의 출력과 새 도구의 출력 차이 |
| 새 명령을 명시적으로 사용 | rg·fd 등 새로운 이름 사용 | 바뀐 구문과 검색 범위를 직접 인식 |

Bash·Zsh의 개인 대화형 설정에서 사용할 수 있는 예다. 설치되어 있지 않으면 기존 설정을 유지하도록 조건을 둔다.

```sh
if command -v bat >/dev/null 2>&1; then
  alias cat='bat --paging=never'
fi
if command -v eza >/dev/null 2>&1; then
  alias ll='eza -l'
fi
```

cat alias는 [bat 공식 문서의 예](https://github.com/sharkdp/bat#automatic-paging)를 따른다. 페이징을 끄더라도 터미널의 구문 강조·줄번호와 원래 cat의 옵션 차이는 남는다. ll은 기존에 쓰던 개인 단축 이름이 있을 때의 예이며, eza의 옵션이 ls와 같다는 뜻은 아니다. Bash·Zsh에서 기본 외부 명령으로 돌아가려면 `command cat 파일`, `command ls`처럼 호출하거나 `unalias cat`으로 alias를 제거할 수 있다. 같은 이름의 shell function이나 PATH 변경까지 사용하는 환경에서는 명령 해석도 함께 확인한다.

반대로 `alias grep='rg'`와 `alias find='fd'`는 이 지도의 기본 도입안으로 권하지 않는다. 검색 범위·조건식·옵션이 달라 기존 입력의 의미가 달라질 수 있기 때문이다. Bash의 비대화형 실행에서는 alias 확장이 기본으로 꺼져 있으며, 개인 shell 설정이 공유 스크립트에 그대로 적용된다고 가정하지 않는다. 이 동작은 Bash 실행으로 확인했다.

따라서 지도에는 “alias 가능”만 적기보다 **어떤 입력을 유지할 수 있는지, 어디서 의미가 달라지는지, 원래 명령으로 어떻게 돌아가는지**를 함께 설명한다.

## 작업의 조합을 바꾸는 경우

[fzf](https://github.com/junegunn/fzf)는 특정 명령어 하나를 대체하기보다 목록에서 대상을 대화형으로 선택하는 기능을 여러 작업에 결합한다. [bat 미리보기 연동](https://github.com/sharkdp/bat#fzf)은 “찾기 → 미리보기 → 선택” 흐름의 예다. 이런 관계는 일방적인 대체보다 보완·조합으로 설명하는 편이 적절하다.

[jq](https://github.com/jqlang/jq)는 JSON 구조를 다루는 도구다. 텍스트 치환 도구와 이름만 대응시키기보다, 입력의 구조를 이해하고 원하는 데이터를 추출하는 문제에 초점을 둔다. 새 도구의 가치는 기존 명령어를 없애는 데만 있지 않다.

## 사용 환경별 선택

아래는 도구 채택률에 대한 통계가 아니라 도입을 판단하는 기준이다.

| 환경 | 기대할 이점 | 함께 확인할 비용 |
|---|---|---|
| 개인 로컬 개발 | 반복 검색·열람·선택에서 편의성 축적 | 설치·업데이트·설정 관리 |
| 여러 원격 서버·임시 환경 | 특정 문제를 해결하는 도구를 선택적으로 사용 | 설치 가능 여부·권한·배포 부담 |
| 공유 자동화·CI | 명시적으로 설치한 도구로 작업 재현 | 버전·옵션·출력·종료 상태의 계약 |
| 기본 도구만 있는 환경 | 익숙한 기본 명령으로 작업 지속 | 새 도구 없이도 수행 가능한 기본 경로 |

새 환경마다 모두 설치해야 한다는 결론도, 새로운 도구를 쓰면 안 된다는 결론도 강제하지 않는다. 개인 환경에서는 개선 도구를 쓰고 공용 환경에서는 기본 도구를 쓰는 선택이 공존할 수 있다. 환경을 재현하는 설정·배포 자동화는 설치 비용을 낮출 수 있지만 기본 설치와 호환성까지 보장하지는 않는다.

## 도구 목록에서 더 살펴볼 항목

현재 지도에 없는 항목을 추후 검토할 수 있도록 원문 목록과 대조했다. 아래는 추가 완료 목록이나 추천 순위가 아니다. 실제 편입 전 공식 자료에서 기능·관계·유지보수 상태를 확인한다.

| 분야 | 추가 검토 대상 |
|---|---|
| 파일·용량 | nnn, ncdu |
| 검색·데이터 | ag, bfs, choose |
| 모니터링·측정 | bottom, glances, gtop, hyperfine |
| 기록·파이프라인 | mcfly, up |
| HTTP | curlie, xh |
| 편집·도움말 | micro, ManKier, explainshell, cheat.sh |
| GUI 경계 | baobab, stacer — CLI와 별도 표시할지 검토 |

이미 포함된 bat·eza·lsd·broot·dust·duf·fd·ripgrep·fzf·delta·jq·sd·procs·gping·zoxide 등은 중복 추가보다 관계와 한계를 보강한다.

[tldr-pages](https://github.com/tldr-pages/tldr)는 예제 중심 자료이며, [tealdeer](https://github.com/tealdeer-rs/tealdeer)는 그 자료를 사용하는 클라이언트 구현이다. 서로를 단순한 명령어 대체 관계로 연결하지 않는다. HTTPie는 프로젝트 이름과 실행 명령 http를 구분해서 검색한다.

## 지도 항목을 읽고 보강하는 순서

1. 같은 문제를 푸는 관계인지, 함께 쓰는 관계인지 확인한다.
2. 무엇이 개선되고 사용 흐름이 얼마나 달라지는지 설명한다.
3. 이점이 있는 작업·환경과 기존 도구를 유지할 조건을 함께 적는다.
4. 실제 계보·유지보수 변화·채택 추세는 기능 비교와 구분하고 근거를 연결한다.
5. 대표 사용 예시는 tldr와 공식 문서로 이어지게 한다.

기존 데이터의 problem·solution·boundary에 구체적인 설명을 보강하는 것부터 시작한다. 변화 단계나 인기 점수를 강제로 추가하지 않는다. 트리의 화살표는 현재 정의된 관계를 뜻하며, 실제 출시 순서·개발 계보·시장 대체를 자동으로 뜻하지 않는다.
