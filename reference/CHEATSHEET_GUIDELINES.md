# Cheatsheet 작성 원칙

> **짧게 설명하고, 구조로 이해시키고, 패턴으로 기억하게 한다.**

Devkit 치트시트는 공식 문서의 축약본이 아니다. **도구의 전체 기능 영역을 거시적으로 조망**하고, 각 기능의 역할·관계·명령 문법·상태 변화를 압축해 보여 주어 처음 보는 명령도 유추할 수 있게 돕는다. 거시적 접근은 기능을 삭제하는 것이 아니라 **넓게 소개하고 세부 명세는 공식 문서에 맡기는 것**이다.

## 작성 기준

1. **작동 모델부터**: 기능 목록을 그리기 전에 **도구가 무엇을 받아, 어떤 대상·상태를 거쳐, 무엇을 바꾸거나 내보내는지** 파악한다. ASCII는 장식이나 목차가 아니라 독자가 도구의 **큰 작동 흐름**을 이해하는 수단이다. 계층·상호작용·데이터 흐름·상태 전이 중 실제 원리에 맞는 표현을 고르고, 그림이 불필요하면 문장으로 대신한다.
2. **ASCII가 본문을 이끈다**: 기존 목차에 그림을 끼워 맞추지 않는다. 먼저 실제 작동 모델을 검증해 ASCII로 설계하고, **그 모델을 기준으로 본문 목차·설명·예시를 다시 구성한다.** 기능이 **어떤 대상에 작용하는지** 드러내고, 포함 계층과 기능 적용 관계를 같은 층으로 나열하지 않는다. 단, 지도 Node와 절을 기계적으로 1:1 대응시키거나 모든 가지에 별도 문서를 만들지 않는다.
3. **기능 발견과 존재 이유**: 주요 기능은 빠뜨리지 않되, **무엇을 해결하는지 → 조작 대상·상태 → 대표 명령**을 연결한다. 익숙하지 않은 기능도 이름과 용도를 알아야 나중에 찾아볼 수 있다.
4. **문법·조합 규칙**: `command [options] target`의 구조, 접두어·약어, 공통 동사와 대상별 패턴을 보여 준다. 모든 옵션을 열거하기보다 처음 보는 명령을 유추할 단서를 남긴다.
5. **이해에 필요한 예시 보강**: ASCII가 나타낸 작동 원리를 본문에서 충분히 설명하고, 부족하면 입력·출력·상태 변화가 드러나는 실제 예시를 추가한다. 기존 예시를 무조건 보존하거나 삭제하지 않는다. 예시 수와 문서 길이에 고정 기준을 두지 않으며, 중복된 예시는 생략한다.
6. **정확한 관계와 표현**: 포함·병렬·의존·실행 순서·데이터 흐름을 혼동하지 않는다. 화살표의 뜻을 명시하고, 정확한 기술용어와 자연스러운 한국어를 사용한다.
7. **문서 경계**: 전체 옵션·버전별 예외는 공식 문서, 원리·심화·장애 사례는 Blog, 개인 설정은 dotfiles에 맡긴다. 문서의 주 목적을 흐리는 상세 설명은 링크로 대체한다.

**핵심:** 명령어를 줄이는 것이 아니라 **기능을 발견하고, 존재 이유를 이해하고, 문법을 스스로 유추하게 하는 것**이다.

## 정보 계층과 문서 소유권

```text
Devkit 도구 지도  → 도구 간 역할·대체·보완 관계
       │
       ▼
Devkit 치트시트   → 한 도구의 기능 영역·관계·공통 명령 문법
       │
       ├─ 공식 문서 → 세부 옵션·전체 명령·버전별 정확한 명세
       └─ Blog      → 내부 원리·설계 선택·설정·실전 문제 해결

dotfiles            → 실제 사용 환경의 설정·재현
```

**거시 → 미시**는 문서의 개수를 늘리라는 뜻이 아니다. 기능을 폭넓게 소개하고, 독자가 더 알아야 할 때만 적절한 하위 자료로 연결한다. 블로그 세부 문서를 반드시 만들 필요는 없으며, 이미 있는 글과 중복되면 링크만 둔다.

## 문서의 기본 흐름

```text
도구의 존재 이유·실제 동작 조사
  → 작동 모델 ASCII 설계·정확성 검증
  → ASCII에 맞춰 본문 구조 재설계
  → 구성 요소·관계·명령·예시 설명 보강
  → 전체 본문과 ASCII 역검증
  → 공식 문서·관련 블로그로 확장
```

- **기능 누락과 세부 생략을 구분한다.** Vim의 Macro·Mark·Fold나 tmux의 Hook·Status Line처럼 독립적인 기능 영역은 소개하되, 모든 키·이벤트·옵션을 열거하지 않는다.
- **명령 체계가 없는 도구에도 억지 문법을 만들지 않는다.** TUI는 조작 대상과 상태, 설정 도구는 적용·병합 순서, 프로토콜 도구는 참여자와 데이터 흐름을 중심으로 설명한다.
- **관계도는 정확한 의미를 가진다.** 계층·접속·의존성·실행 순서·데이터 흐름을 혼합하지 않고 무엇을 나타내는지 명시한다. 예를 들어 tmux Client의 Server 접속과 Session→Window→Pane 포함 계층은 구분한다.
- **독자가 스스로 추론하도록 한다.** 대표 명령은 기능 발견의 단서이므로 무조건 줄이지 않는다. 예제는 실제 동작을 밝힐 때만 남긴다.

## 이동·병합·삭제 판단

| 내용의 성격 | 관리 위치 |
|---|---|
| 도구의 기능 영역·공통 문법·상태 모델 | Devkit 치트시트 |
| 도구 선택·대체·보완 관계 | Devkit 도구 지도 |
| 장애 원인·복구 절차·특정 설정·운영 사례 | Blog (기존 글 우선) |
| 전체 명령·옵션·버전별 동작 | 공식 문서 |
| 개인 환경에 종속된 설정 | dotfiles |

독립적인 기능 지도가 없는 문서는 병합·이동·삭제할 수 있다. 단, **삭제 전에 고유한 내용과 기존 참조를 확인**한다. 원본을 옮긴 뒤 카탈로그·인덱스·내부 링크를 수정하며, 내용을 복제한 두 문서를 동시에 유지하지 않는다.

## 분량과 편집

- **넓은 기능 범위와 필요한 만큼의 설명 깊이**를 우선한다. 문서 길이·명령 수·예시 수 자체를 목표로 삼지 않는다.
- **한눈에 이해되는 최소 분량**을 우선한다. 문단보다 짧은 표·ASCII·주석 달린 예제를 쓴다.
- 같은 명령을 '핵심', '30초', '전체 목록'에서 반복하지 않는다.
- 한 번 배운 규칙으로 여러 명령을 추론할 수 있는 설명만 추가한다.
- 명령어는 존재 이유와 함께 소개한다. 설치 안내 복제, 목적 없는 명령 나열, 장황한 내부 원리 설명은 피한다.
- 도구마다 구조가 다르므로 형식을 강제하지 않는다. CLI는 문법, 설정 도구는 적용 순서, TUI는 조작 계층을 중심으로 정리한다.

## 완료 전 검증

- 문서 **전체**를 읽어 상단의 작동 모델이 실제 동작을 설명하는지, 본문이 그 모델의 대상·관계·상태를 **빠짐없이 충분히** 확대하는지 확인한다. 본문에 없다는 이유로 중요한 ASCII Node를 제거하지 말고 설명을 보강한다. 단순 기능 목록을 ASCII로 옮긴 것이라면 구조를 다시 설계한다.
- 기본값·버전 조건·약어·명령 실행 결과는 공식 문서 또는 실행 가능한 환경에서 확인한다. 검증하지 못한 항목은 단정하지 않는다.
- 개념 지도는 **역할 관계**와 **실제 실행 순서**를 혼동하지 않도록 표시한다. 그림과 본문이 같은 내용을 반복한다면 한쪽을 줄인다.
- 동일 개념을 여러 곳에서 반복하거나, 설치·운영 사례가 명령 문법의 중심을 가리지 않는지 확인한다.
- 병합·삭제 시 `reference/catalog.json`, 인덱스, 다른 문서의 상대 링크와 참조를 함께 점검한다.
- 앞부분만 수정한 경우 **부분 개편**으로 표시하고, 전체 검증 완료라고 주장하지 않는다.

## 경계

- **Devkit**: 명령어를 이해하고 추론하는 압축 레퍼런스 및 도구 관계.
- **Blog**: 내부 원리와 심화 학습.
- **dotfiles**: 실제 개인 설정과 재현.
- **공식 문서**: 전체 명세와 최신 동작.

## 검토 질문

> 상단 ASCII만 보고도 **이 도구가 어떤 대상과 흐름으로 작동하는지** 설명할 수 있는가? 본문을 읽고 기능의 존재 이유와 대표 명령을 연결해, 더 찾아볼 키워드와 문법을 스스로 유추할 수 있는가?

그렇지 않다면 예시·명령을 무조건 늘리거나 줄이지 말고 **구조와 설명의 역할부터 보정한다.**
